# 함선 성장 재료 관리 앱: 의도와 작업 기준

## 한 줄 정의

검은사막의 여러 무역선·구축함·중범선을 동시에 추적하면서, **공유 재고를 기준으로 각 성장 단계의 재료 부족분과 까마귀 주화 비용을 계산하는 개인용 정적 웹앱**이다.

## 해결하려는 문제

한 캐릭터가 중범선을 여러 척 운용할 수 있다. 선박별 목표와 단계는 다르지만 재료 보유량은 하나의 공용 창고/인벤토리 재고로 관리된다. 따라서 단일 장비의 진행률만 보는 방식이 아니라, 함대 전체 목표에 대해 다음을 정확히 보여줘야 한다.

- 재료별 총 필요 수량, 현재 보유량, 부족 수량
- 부족분을 까마귀 주화로 구매할 때 필요한 주화 수
- 재료가 어느 선박의 어느 제작/증축식에 쓰이는지
- 각 재료의 획득처(일일·주간 의뢰, 물물교환, 가공 등)

## 데이터 경계

### 고정 게임 카탈로그

`src/catalog.ts`는 게임 제작식의 단일 기준 데이터다. 다음은 사용자가 앱 UI에서 변경할 수 없다.

- 재료 이름 및 식별자
- 까마귀 주화 단가
- 획득처
- 단계별 제작/증축 레시피와 필요 수량

카탈로그를 수정할 때는 공식 검은사막 모험가 가이드 또는 신뢰 가능한 아이템 DB로 검증한다. 아이템명·Codex ID·까마귀 주화 가격은 `src/data/items.ts`의 단일 아이템 DB에 공식 패치 원문 URL과 함께 보관한다. 가격을 확인하지 못한 재료는 `crowCoinPrice`를 생략한다. 이 경우 UI는 `—`를 표시하며, 추측한 가격을 넣지 않는다.

참고: 이전에 제공된 스프레드시트는 데이터 확인을 위한 참고 자료일 뿐이다. 앱은 해당 Google Sheet를 읽거나 동기화하거나 UI에 노출하지 않는다.

### 사용자 진행 데이터

브라우저/Drive에 저장되는 것은 `AppData` 프로필뿐이다.

- `ships`: 사용자의 함대 목록(이름, 선체 유형, 현재 추적 단계)
- `inventory`: 재료 ID별 공유 보유 수량
- `updatedAt`: 충돌 판단용 수정 시각
- `materialSort`: 전체 재료 표의 정렬 컬럼 및 방향
- `supplyPlans`: 수행 예정인 일일·주간 의뢰와 선택 보상
- `completedTasks`: 이전 버전의 수령 기록 호환용 데이터

일일·주간 수급 원본은 `src/data/quests.ts`의 Codex 검증 카탈로그다. 각 항목은 문자열 Codex 의뢰 ID, 시작 지역/NPC, 목표, 보상과 충돌 의뢰 ID를 가진다. URL은 `src/data/codex.ts`에서 ID로 조합한다. ID나 보상을 직접 확인하지 못한 의뢰는 활성 수급 계산에서 제외한다. 상세 검증 규칙은 `docs/CODEX_QUEST_DATA.md`에 기록한다.

일일·주간 의뢰는 재고를 자동으로 늘리는 수령 기록이 아니라 **수급 계획**이다. 사용자가 수행할 의뢰와 선택 보상을 저장하면 재료별 일일 수급, 주간 수급, 그리고 `부족량 ÷ (일일 수급 + 주간 수급 ÷ 7)`의 완료 예상이 계산된다. 실제 보유량 변화는 재료 표의 보유 수량 입력 또는 수동 추가로만 기록한다.

사용자는 선박 인스턴스를 자유롭게 추가·이름 변경·제거하고 보유 수량을 입력할 수 있다. 이것은 게임 레시피 편집 기능이 아니다.

## 도메인 모델

### 선체 유형

`trade`, `warship`, `balance`, `advance`, `volante`, `valor`를 사용한다.

- 무역선 → 중범선 균형 / 점진
- 구축함 → 중범선 비상 / 용맹

중범선은 여러 척을 독립 인스턴스로 추가할 수 있다. 예: `중범선 점진 A`, `중범선 점진 B`, `중범선 용맹 A`.

### 성장 단계

1. 무역선/구축함 증축
2. 무역선/구축함 파템 제작
3. 중범선 증축
4. 중범선 파템 제작
5. 중범선 노템 제작

무역선/구축함은 `중범선 증축 목표`를 각각 균형·점진 또는 비상·용맹 중 하나로 선택한다. 이 선택은 3단계 증축식과 이후 목표 합산에 반영된다. 따라서 3단계 증축을 열면 파템 4종뿐 아니라 해당 중범선 증축에 필요한 화려한 암염 주괴, 화려한 진주 결정, 심해의 눈물 등의 재료도 함께 보인다. 중범선을 여러 척 따로 추적하려면 중범선 인스턴스를 별도로 추가한다. 향후 제작 완료를 트랜잭션으로 기록하는 기능을 만들 경우, 하위 재료를 차감하고 결과 장비/선박을 자동 생성하는 방식이어야 한다. 단순 완료 체크박스는 진행 상태를 왜곡하므로 피한다.

## 계산 규칙

- 재료 보유량은 `inventory[materialId]` 하나만 사용하며 함대 전체에서 공유한다.
- `필요량`: 선택한 범위에 속하는 모든 선박 레시피의 수량을 합산한다.
- `부족량 = max(필요량 - 보유량, 0)`
- `재료 진행률 = min(보유량 / 필요량 × 100, 100)`이며 정수로 표시한다.
- 레시피 진행률은 해당 레시피 재료 진행률의 산술 평균이다.
- 부족분 주화 = `부족량 × crowCoinPrice`. 단가가 없는 재료는 합계에 포함하지 않고 `—`로 표시한다.
- 전체 재료 탭의 `현재 단계만`은 각 선박의 `activeStage`만 합산한다.
- `남은 전체 목표`는 각 선박의 현재 단계 이후 모든 레시피를 합산한다.
- 전체 재료 표는 이름, 필요/보유/부족 수량, 진행률, 개당·부족분 까마귀 주화, 사용처를 정렬할 수 있으며 선택값은 프로필·Drive·JSON 백업에 저장된다.
- `일일 수급` 탭의 체크는 의뢰를 수행할 **계획**에만 포함한다. 재고를 자동으로 늘리지는 않으며, 선택 보상도 계획한 한 가지만 수급량 계산에 반영한다.
- 예상 일수는 현재 부족량을 등록된 일일 보상과 주간 보상의 일 평균치(주간 보상 ÷ 7)로 나눈 올림값이다. 모든 표시된 수급처를 빠짐없이 완료하고 선택 보상도 해당 재료를 선택한다는 가정이며, 물물교환·드롭·가공은 포함하지 않는다.
- 수동 추가는 의뢰 체크와 별도로 동작하며, 입력한 양을 현재 공유 보유량에 **더한다**. 직접 보유 수량을 고쳐야 할 때는 재료 표의 `보유` 입력을 사용한다.

## 화면의 역할

| 화면 | 목적 |
| --- | --- |
| 함대 현황 | 함선 카드, 현재 단계 진행률, 현재 단계의 부족 재료 상위 목록 |
| 선박 단계 | 한 선박의 단계별 고정 레시피 및 재료 보유량 입력 |
| 전체 재료 | 함대 전체 합산, 부족량·진행률·주화 비용 및 레시피 사용처 |
| 일일 수급 | 일일·주간 의뢰 수행 계획, 재료별 예상 수급량, 수동 추가 |
| 수급 도감 | 재료별 까마귀 주화 단가와 획득처를 읽기 전용으로 제공 |
| 함대·백업 | 함대 인스턴스 관리, Google Drive 연결, JSON 백업/복원 |

## 저장과 동기화

LocalStorage가 항상 기본 저장소다. Google Drive 연동은 선택 사항이며 Google Identity Services의 브라우저 토큰만 사용한다.

- 권한: `https://www.googleapis.com/auth/drive.appdata`만 요청
- 파일: `appDataFolder/bdo-ship-materials.json` 하나
- Client Secret은 절대 사용하거나 저장하지 않음
- 변경 후 약 1.5초 debounce로 Drive 자동 저장
- 시작 시 로컬과 Drive의 `updatedAt`을 비교
- 두 값이 다르면 더 최신 쪽을 권장하되, 사용자가 어느 쪽을 덮어쓸지 선택
- 오류가 나도 LocalStorage 저장은 계속 유지
- 연결 해제는 현재 브라우저의 Drive 연결 상태만 지우며 로컬 데이터는 보존

## 구현 파일 안내

- `src/catalog.ts`: 고정 게임 데이터 및 레시피
- `src/types.ts`: 카탈로그·프로필 타입
- `src/utils.ts`: 집계, 부족분, 진행률 계산
- `src/storage.ts`: LocalStorage 및 프로필 JSON 검증/마이그레이션
- `src/useDriveSync.ts`, `src/drive.ts`: Google Drive 앱 전용 폴더 동기화
- `src/App.tsx`: UI와 사용자 상호작용

## 변경 작업 시 지켜야 할 원칙

1. 고정 카탈로그와 사용자 프로필을 섞지 않는다.
2. 함선별 재료를 단순히 독립 재고로 만들지 않는다. 모든 보유 수량은 공유된다.
3. 알려지지 않은 가격·레시피를 추측으로 채우지 않는다.
4. 데이터 소스를 업데이트할 때는 카탈로그를 수정하고, 기존 사용자의 `inventory` 키 호환성을 고려한다.
5. JSON 내보내기/가져오기는 사용자 진행 데이터만 대상으로 한다.
6. UI 변경 후 `npm run build`를 통과시키고, Pages 배포 시 `VITE_BASE_PATH`를 유지한다.
